# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Purpose

This is a **documentation + workspace repository** for building LineageOS-based custom ROMs for the **Xiaomi Redmi Note 10S** (codenames: `rosemary`, `rosemary_p`, `maltose`, `secret`; SoC: MediaTek MT6785/Helio G95). It contains no buildable source itself — only Markdown reference material and a `.gitignore` that reserves paths for cloned upstream sources.

There are no build, lint, or test commands at this repo's level. All build activity happens inside a separate AOSP/LineageOS source tree (typically `~/android/lineage/`) that this repo's documentation directs the user to set up.

## File Layout

- `README.md` — end-to-end LineageOS build guide for rosemary. Covers Ubuntu prereqs, the `repo init` / `breakfast` / `brunch` workflow (with modern `repo sync` speedup flags), ccache setup (mandatory `CCACHE_EXEC=$(which ccache)` since Android Q), build identity env vars, and a rosemary-specific flashing-pitfalls section (codename trap across rosemary/rosemary_p/maltose/secret, vbmeta disable, separate dtbo flash, MTK 4.19 non-GKI kernel). Also covers signing keys for distributable builds and MindTheGapps for adding Google apps.
- `LineageOS_UI_Customization_SKILL.md` — reference for modifying SystemUI, `frameworks/base`, and `packages/apps/Settings`. Covers RROs (classic and Soong `runtime_resource_overlay`), Android 11+ `overlay-config.xml` partition precedence, runtime overlay control (`cmd overlay`, `idmap2 dump`), **Fabricated RROs** (Android 12+ runtime overlay generation), the **Material You / Monet** pipeline, the Android 15+ **SystemUI Compose / Scene Framework** migration, LineageOS-specific infrastructure (`LineageSettings` provider, `lineage-sdk` Styles API, `LineageParts`, Trebuchet vs Launcher3, `SystemUIExt` vendor-extension pattern), and ROM-adjacent customization (PixelPropsUtils / Play Integrity).
- `ROM_Debugging_SKILL.md` — reference for build-type selection (`user`/`userdebug`/`eng`), kernel logging via **`/sys/fs/pstore/`** (the legacy `/proc/last_kmsg` path was removed upstream — do not recommend it), `logcat`/`dumpsys`/`bugreport`, tombstones, persistent logging, thermal debugging, **Perfetto** system tracing, **simpleperf** CPU profiling, **Scudo / GWP-ASan** native memory bug detection, **MTK AEE** crash collection (`/data/aee_exp/db.*`) and UART serial-console access for preloader/`lk` panics on MT6785, plus modern workflow tips (Android 11+ wireless ADB pairing, per-tag log control via `setprop log.tag.*`, `am compat` for behavior-change isolation, Magisk/KernelSU caveats during ROM debugging).
- `.gitignore` excludes `/device/`, `/kernel/`, `/hardware/` — these paths are intentionally reserved for the user to clone the device-specific upstream repos into this working directory if they choose to use it as a partial workspace. As of lineage-22.2+ the LineageOS-blessed path is `breakfast rosemary`, which clones all of these automatically into `~/android/lineage/` via the manifest's `roomservice.xml` — the manual clones documented in `README.md` §2 are only needed for AOSP-base (non-Lineage) builds.

If those directories are absent in this repo, that is the expected state of a fresh clone — not a bug.

## How to Work in This Repo

- **Documentation edits**: treat the two `*_SKILL.md` files and `README.md` as the actual deliverables. They are written as standalone reference docs intended to be consumed outside this repo (e.g., by other Claude instances or developers reading on GitHub), so preserve their self-contained tone and don't introduce cross-references that assume the reader has the rest of the repo open. The one allowed cross-doc reference is README → SKILL docs and vice-versa, used sparingly when a topic is owned by the sibling doc (e.g., the debugging doc points to the customization doc for `cmd overlay`).
- **Device-specific facts** that belong in the docs: rosemary uses the MT6785 kernel tree (Linux 4.19, MTK vendor fork — **not** GKI; `/sys/fs/pstore/console-ramoops-0` is where last-boot kernel logs live). The LineageOS build target is **single** — `breakfast rosemary` / `brunch rosemary` works for all five physical Xiaomi codenames (`rosemary`, `maltose`, `secret`, `rosemaryp`, `secretr`); `init_rosemary.cpp` detects the running variant at boot. Where the variant *does* matter is (a) which stock MIUI firmware to flash as a fallback / rollback target (see "MIUI firmware baseline" below), and (b) which blob set `extract-files.py` should pull from — though most builders skip extract entirely and clone `TheMuppets/proprietary_vendor_xiaomi_rosemary` (lineage-23.2 branch) into `vendor/xiaomi/rosemary/` instead. Other pitfalls: needs vbmeta verification disabled to flash unsigned (testkey) boot images, flashes `dtbo.img` separately from `boot.img`, and requires Mediatek + Xiaomi HAL repos plus `device/mediatek/sepolicy_vndr` in addition to the device tree (all pulled automatically by `breakfast` — but `vendor/xiaomi/rosemary` is **not**; that must be cloned separately or generated by `extract-files.py`).
- **The brunch zip ships firmware (`ships_fw: true`).** A successfully built rosemary OTA zip contains a 21-partition `payload.bin`: not just `system/vendor/product/system_ext/boot/dtbo`, but also `md1img` (modem), `lk`, `gz`, `scp`, `sspm`, `spmfw`, `tee`, `audio_dsp`, `cam_vpu{1,2,3}`, `preloader_raw`, and all three `vbmeta*` partitions. Both [rosemary_variant1.yml](https://github.com/LineageOS/lineage_wiki/blob/main/_data/devices/rosemary_variant1.yml) and `rosemary_variant3.yml` confirm `ships_fw: true`. **Size:** a complete lineage-23.2 OTA zip is **~1.1-1.5 GB** (verified 2026-05-24: 1131 MB zip, payload v2, all 21 partitions present); older Internet guides citing 3-4 GB pre-date modern payload compression and shouldn't be treated as a missing-partition red flag. Implication: **a user does NOT need to flash MIUI stock firmware as a prerequisite to installing LineageOS** — the OTA payload writes the modem/preloader/lk/etc partitions itself during sideload. The MIUI fastboot ROM is only needed as a (a) fallback rollback target, or (b) prerequisite if their phone is on a pre-MIUI-13 baseline that the modern bootimg can't satisfy. Verify a fresh build's payload partition list with the §4 step-5 check in `README.md` before recommending a flash; if `md1img` is absent the build is broken and the phone will have no cellular post-flash. (For a quick manifest-only inspection without unzipping: `python3 ~/android/lineage/system/update_engine/scripts/payload_info.py <(unzip -p ROM.zip payload.bin)` — pass `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python` if protobuf complains about generated-code-too-old; note the script needs a seekable file so wrap with `bash -c 'unzip -p ROM.zip payload.bin > /tmp/p.bin && payload_info.py /tmp/p.bin'` if process substitution doesn't work.)
- **MIUI firmware baseline: TFF, not TKL.** `init_rosemary.cpp` carries `V14.0.11.0.TKLMIXM` as the maltose-variant *fingerprint string label*, but the LineageOS wiki firmware-update page for all rosemary variants (variant1 Global / variant2 NFC / variant3 LATAM) points to a single canonical fastboot ROM: `V14.0.17.0.TFFMIXM` (global TFF region, filename `miui_ROSEMARYPGlobal_V14.0.17.0.TFFMIXM_b6ba1e953f_13.0.zip`, ~6 GB). Do not over-index on the TKL string in init — it's just what gets set as `ro.build.fingerprint` at boot for the maltose variant, not a constraint on which partition images the user must flash. When recommending a stock firmware download, default to TFF unless the user's specific phone refuses it.
- **Vendor blobs are not auto-cloned.** `breakfast rosemary` brings down `device/`, `kernel/`, `hardware/`, and `sepolicy_vndr/` but does **not** add `TheMuppets/proprietary_vendor_xiaomi_rosemary` to `roomservice.xml`. The first `breakfast rosemary` will therefore fail with `vendor/xiaomi/rosemary/rosemary-vendor.mk does not exist` and the misleading `Don't have a product spec for: 'lineage_rosemary'` — this is expected. Land the vendor blobs (clone TheMuppets per `README.md` §2.C, then add the project entry to `.repo/local_manifests/roomservice.xml` so future syncs keep it updated) and re-run `breakfast rosemary`. **The MTK radio firmware in TheMuppets is Git-LFS-tracked** (audio_dsp.img, md1img.img, lk.img, gz.img, cam_vpu*.img, scp.img, tee.img, etc. — ~77 MB total). A plain `git clone` leaves you with ~100-byte LFS pointer files; the build then fails at kati with `radio/audio_dsp.img SHA1 mismatch`. Always `git lfs install && git lfs pull` after cloning (or pass `--git-lfs` to `repo init`). **LineageOS itself also ships LFS-tracked prebuilts** — `external/chromium-webview/prebuilt/{arm,arm64,x86,x86_64}/webview.apk` (~247 MB for arm64 alone). Without `--git-lfs` at `repo init`, those come down as ~130-byte pointer files and the build dies *hours later* at `//external/chromium-webview:webview verify <uses-library>` with `aapt2 ... failed opening zip: Invalid file.` This is independent from the TheMuppets LFS issue — `--git-lfs` on the parent `repo init` covers chromium-webview but NOT `vendor/xiaomi/rosemary` (which lives outside the manifest); both need LFS pulled. The `extract-files.py` path is also valid but is for device-tree maintainers regenerating the blob set against a specific stock MIUI build — it has a known firmware-double-move bug in extract_utils on lineage-23.2 (patch at `patches/0001-extract_utils-fix-firmware-double-move.patch`), and its smali patches against MTK IMS/WFC APKs may not apply against MIUI builds newer than the device-tree maintainer used.
- **Shell-aliasing gotcha when running breakfast/lunch from Claude Code:** lunch's single-arg parser uses `echo $1 | grep "-"` to detect the legacy `product-release-variant` form. Claude Code's interactive shell wraps `grep` as a function that re-routes to a different tool (which rejects a bare `-` as a pattern), so the test returns empty, lunch falls through to the new-format branch, and treats the whole `lineage_rosemary-bp4a-userdebug` as `TARGET_PRODUCT`. Always `unset -f grep` after `source build/envsetup.sh` (or pass three explicit args: `lunch lineage_rosemary bp4a userdebug`). On a normal user shell this is a non-issue.
- **Branch names**: LineageOS releases for rosemary are `lineage-20`, `lineage-21`, `lineage-22.2` (A15 QPR2), `lineage-23.0`, `lineage-23.2` (A16 QPR2 — current rolling default). There is **no** `lineage-22.0` or `lineage-23.0`-without-suffix; Lineage skipped to `.2` rebases for those releases. Don't fabricate branch names — verify against the [rosemary device page](https://wiki.lineageos.org/devices/rosemary/) if uncertain.
- **Don't fabricate commands** for building, flashing, or testing at this repo's root — there is nothing here to build. Any build instructions you add should be framed as "run this in your AOSP tree" and match the conventions already in `README.md` (i.e., `breakfast rosemary` / `brunch rosemary` for the LineageOS-blessed path, with raw `lunch lineage_rosemary-userdebug` + `mka bacon` as the lower-level alternative; `repo sync -c --no-clone-bundle --no-tags --optimized-fetch --prune -j$(nproc --all)` for first syncs).
- **Self-correction loop — fix the docs when they break you.** If you're executing a command or following a step from `README.md`, `LineageOS_UI_Customization_SKILL.md`, or `ROM_Debugging_SKILL.md` and it fails, produces no effect, or turns out to be wrong (e.g., a flag was removed in a newer LineageOS branch, a path moved, a tool was renamed, a kernel config no longer exists), **update the doc in the same turn before moving on**. The docs are the source of truth for future sessions — leaving them stale means the next Claude instance (or human) hits the same wall. Patterns to apply:
  - Replace the wrong instruction with the working one *and* add a short "**Note:**" sentence explaining what changed and why, so a reader who finds an older guide elsewhere can reconcile the difference (see the `/proc/last_kmsg` → `/sys/fs/pstore/` note in `ROM_Debugging_SKILL.md` §5 as the template).
  - If the wrong instruction is something a research agent already flagged in a previous session, also update `CLAUDE.md`'s "Device-specific facts" or "Branch names" bullets so the correction is visible from the file Claude always loads.
  - Don't silently delete a wrong instruction — keep the correction visible, because part of these docs' value is teaching readers what *not* to do.
  - If you can't determine the correct instruction (the original was wrong but you don't know the right answer yet), mark it with `<!-- TODO: verify ... -->` inline rather than deleting it, and surface that TODO to the user.
